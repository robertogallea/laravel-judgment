# Recording an Assessment is required by default

Extends ADR-0003. Recording can fail after the paid Engine round, and before this decision that failure escaped `assess()` and `decide()` as a raw `QueryException`. `judgment.persistence.required`, on by default, makes auditing mandatory: an Assessment or Outcome that cannot be recorded is refused with `AssessmentNotRecorded`, because the oversight ADR-0003 cites (GDPR Art. 22, the AI Act) means no unrecorded consequential judgment is acted on. The exception carries the Assessment so the answers are not lost. It bypasses `judgment.throw_on_failure`, since the Engine did answer, and Unassessed stays strictly an Engine failure. Writing the Outcome in `decide()` follows the same rule, as does deciding the Assessment the exception carries, so an unrecorded Outcome is never acted on either. A queued assessment that cannot be recorded fails its job, losing the answers, and a retry pays for another Engine round. That makes deciding a linked Assessment depend on the database, which a pure Decision does not (ADR-0004), but only for Assessments a Judge recorded. Turning the switch off makes auditing best-effort for applications that prefer to keep working through a database outage. Failures are then reported and logged, and the audit trail has gaps.

Recording an Unassessed attempt is always best-effort, as decided in ADR-0014.
